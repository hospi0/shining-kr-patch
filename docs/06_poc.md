# PoC (한글 표시) 착수 — 진행 중 (2026-07-12)

목표: 우회훅 재삽입 메커니즘 검증을 위한 최소 가시성 게이트 = **한글 1자 화면 출력**.
접근: 세이브스테이트의 렌더된 텍스트 비트맵에 한글 글리프를 그려넣고 리팩→로드(또는 디코드버퍼 주입).

## 확인된 것
- **세이브스테이트 파싱 OK**: RZIP→6.85MB 스냅샷(`tools/parse_state.py`). Mednafen 섹션 태그: VDP1@0x4A8A, VDP2@0x4BF7, VRAM@0x7B81D, CRAM@0x2FC764.
- **글리프 픽셀 값 = 0x00/0x07/0x16**(docs/03 재확인): 스냅샷 0x341249 영역이 정확히 이 3값만 가짐(배경0/외곽0x07/본체0x16 추정).
  - ⚠️ 단, 16KB(0x341249~0x345249)에 **비영 픽셀 204개뿐** → 대사 한 줄(33자, ~1500px) 치곤 너무 적음. **이 위치는 메인 대사 비트맵이 아니라 staging/work 버퍼(마지막 몇 글자만)로 추정**(0x06084000 staging은 글자별 재사용).
- **오배제**: 64KB 최대 diff(0x3ed290)는 RGB555 렌더 시 노이즈 → 프레임버퍼 아님(오디오/데이터 추정). s1↔s3 diff의 소규모 영역(0x341249/0x387290/0x603e21 등 ~877B 페어)이 텍스트 관련이나 전부 저밀도.

## 막힌 지점 = 글리프 렌더 포맷/소스 (= 미해결 "폰트 문제")
- 렌더된 **메인 대사 비트맵의 정확한 스냅샷 위치·포맷(bpp·스트라이드) 미확정**. VDP2 VRAM base를 Mednafen 섹션 구조로 정밀 파싱 안 함(0x2FCA49 추정은 저밀도라 불확실).
- 렌더러는 다층(라인매니저 0x606bDC0=VRAM/staging=base+line×512, 글리프 드로우는 [0x06065018] 등 다층 UI). 글리프 **비트맵 소스**(index→bitmap)는 여전히 미추적 = docs 기록의 미해결 한자 폰트 소스와 동일 문제.
- **PoC는 근본적으로 폰트(글리프 비트맵 포맷·소스)를 알아야 함** — 우회훅으로 인덱스는 주입해도, 그 인덱스의 한글 비트맵이 어딘가 있어야 렌더됨.

## 🎉 폰트/글리프 포맷 완전 해독 (2026-07-12, 코드 트레이스) — **PoC 핵심 돌파**
블라인드 렌더링 대신 렌더러 코드를 트레이스해 결정적으로 규명(tools/font.py).

**렌더 콜체인**: 메시지렌더 `0x606c9e4`(seek 0x606cb84로 메시지 디코드) → 글리프루프(디코드버퍼 0x0607b390 읽어 토큰별) → 토큰>0x1F면 글리프드로우 `0x606d408` → 블릿 `0x606d4e0` → 1bpp디컴프 `0x606d684`.

**글리프 테이블 위치** (0x606d408에서):
- `R2 = [0x218000]` (=런타임 0x21800c), `R1 = (glyph_idx − 0x20) × 32`, 엔트리 = `R2 + R1`.
- 즉 **글리프 테이블 = `[0x218000]값 + (glyph_index − 0x20) × 32`**, 글리프당 **32바이트**.

**글리프 엔트리 포맷 (32바이트)** — ✅검증:
- `[0]=word0` = **글리프 폭(px)**. (を=12, 。=6, ？=9, 공백=8)
- `[2..31]` = **15행 × 16비트 BE, 1bpp 비트맵**(MSB=왼쪽). 글리프는 보통 상단~12px 사용.
- 디컴프(0x606d684)가 1bpp→8bpp로 전개(색=[0x0607BB90] 글리프 팔레트, 본체 0x16).
- **검증**: を/あ/？/た/。 엔트리를 이 포맷으로 렌더→해당 문자 정확 표시(extract/state2/font_test.png).

**한글 삽입 실증**: 12px "가"를 이 32바이트 포맷으로 인코딩(`tools/font.py` encode_glyph)→디코드 렌더가 を·あ와 같은 스케일 한글로 표시됨(extract/state2/hangul_test.png). **즉 한글을 게임 폰트 포맷으로 제작 가능 확정.** (디자인 품질은 폰트 전략 단계서 정제.)

**⚠️함의 — 글리프도 컴파일러 산출**: 글리프 테이블이 메시지 영역(0x218000, 씬 진입 시 컴파일러가 codebook_B와 함께 빌드) 안에 있음 → 폰트 소스를 따로 못 찾았던 이유. 재삽입은 **우회훅으로 (1)한글 글리프 32B 엔트리를 슬롯에 주입 + (2)디코드 스트림에 그 인덱스 주입** 두 가지를 함께.

**남은 PoC 완료 작업**: (1)한글 글리프 디자인 정제, (2)슬롯 배치+인덱스 주입 방식(스냅샷 편집 or 훅) 결정, (3)RZIP 리팩(미구현) 또는 훅, (4)에뮬 로드 검증.

## ✅ PoC 스테이트 제작 완료 (2026-07-12) — 에뮬 로드 검증 대기
1. **RZIP 리팩 구현·검증**: `tools/repack_state.py`. 파싱→리팩→재파싱 스냅샷 **바이트 완전 동일**(roundtrip OK).
2. **글리프 테이블 스냅샷 위치**: LWRAM 0x218000 → snap `0x4973ca`(swap16). 엔트리 = 0x4973ca+(addr−0x218000), addr=0x21800c+(idx−0x20)×32.
3. **한글 글리프 주입**: "가"(12px, tools/font.py 인코딩)를 state1 스냅샷의 글리프 슬롯 **た(0xe0)/か(0x96)/し(0x9c)/な(0xe5)/り(0xf8)/い(0x92)** 6개에 덮어씀(swap16). 편집 후 디스왑·디코드로 0xe0=가 확인, 미편집 を(0x86)=を 유지 확인.
4. **산출**: `poc/Shining the Holy Ark (Japan) (3M).state4` (RetroArch 슬롯4). 편집 스냅샷 roundtrip OK.
5. **목업**: 편집 글리프테이블로 대사 일부 렌더 → お[가][가] あ[가]ら[가][가]っ[가] (extract/state2/mockup.png) = 한글이 게임 폰트로 정확 렌더 확인.
- **원리**: 렌더러(0x606d408)가 매 글리프마다 `[0x218000]`서 테이블 재읽음 → 편집된 글리프테이블이 다음 렌더에 반영. 현재 대사줄은 이미 VRAM블릿돼 정적이므로 **로드 후 대사 1스텝 진행하면** 다음 줄이 편집 글리프로 렌더돼 "가" 표시(즉시 재렌더되면 바로 표시).
- **검증 대기**: 사용자가 RetroArch에 로드→대사 진행→"가" 화면 출력 확인. 확인되면 **PoC 게이트 통과 = 우회훅 재삽입 경로 실증**.

## 렌더 포맷 조사 (2026-07-12) — (초기 블라인드 렌더링, 위 코드트레이스로 대체됨)
- **렌더러 작동 확인**: 스냅샷 WRAM `0x48f000`(WRAM Low 0x20FC36)를 **폭 48바이트 8bpp 선형**으로 렌더 → **엘프 캐릭터 스프라이트** 육안 확인(스크린샷의 그 캐릭터). 즉 캐릭터 그래픽 = WRAM에 48바이트폭 8bpp.
- **대사창 배경** = `0x367000`대(VDP2), **16바이트 반복 가로줄 패턴**(스크린샷 초록박스 텍스처)로 렌더됨. 텍스트 아님.
- **자기상관 스트라이드**: 스프라이트 영역 48바이트 배수(48/96/144/192/240). VDP2 배경영역은 16.
- **VDP2 VRAM 위치**: Mednafen 필드 태그 `VRAM`@0x2fc71e/0x2fc7b1/0x2fc7f7(뱅크 여럿?), VDP2 데이터 ~0x2fc7fb 시작.
- **⚠️핵심 미해결**: docs/03 추정 텍스트영역(VDP2 0x44800→snap 0x340800~0x345800)은 **20KB에 비영 204바이트뿐** = 실제 렌더된 대사 텍스트가 거기 없음. **대사 텍스트는 VDP1 스프라이트(프레임버퍼) 또는 아직 못 찾은 VDP2 뱅크로 렌더 추정.** 블라인드 스냅샷 렌더링으로는 텍스트 비트맵 위치·스트라이드 미수렴.
- **픽셀값 = 0x00(배경)/0x07(외곽)/0x16(본체)**. 4bpp(니블 0,1,6,7) 또는 8bpp 팔레트 인덱스 — 미확정.

## 다음 단계 (PoC 완료 경로)
0. **(권장) 렌더러 코드 트레이스로 결정적 규명**: 블라인드 렌더링 대신 글리프 블릿 루프 추적. 라인매니저 `0x606bDC0`(VRAM dest=struct+24=0x25E44000+line×512, staging dest=struct+28=0x06084000+line×512). struct+28(staging) 읽어 픽셀 쓰는 블릿 루프를 찾으면 글리프 소스주소+포맷(bpp·크기) 확정. 또는 대사가 VDP1 스프라이트면 VDP1 커맨드테이블 추적.
1. **VDP2 VRAM 정밀 위치**: Mednafen 상태 섹션(VDP2@0x4BF7) 구조 파싱해 512KB VRAM 데이터 정확 오프셋 확정 → text VRAM(0x25E44000→VDP2 0x44000/0x44800) 실제 스냅샷 위치 확정 → 렌더로 "どおりで" 육안 확인 → bpp/스트라이드 확정.
2. **글리프 비트맵 소스 규명**(폰트 문제): 렌더러의 index→bitmap 경로 추적(라인매니저 0x606bDC0 역방향, 또는 staging 0x06084000에 픽셀 쓰는 루프). 가나 고정슬롯 비트맵 시트 위치 특정.
3. **한글 글리프 디자인**: 확정된 bpp/크기(12×12 8bpp 추정)로 한글 음절 1자 비트맵 제작.
4. **주입**: (a) staging/VRAM 직접 페인트 후 RZIP 리팩→로드(가시성 게이트), 또는 (b) 폰트 시트 슬롯에 한글 비트맵 + 디코드버퍼 인덱스 세팅(파이프라인 검증).
5. RZIP **리팩 기능** 추가 필요(parse_state.py는 파싱만; zlib 청크 재압축 리팩 구현).
