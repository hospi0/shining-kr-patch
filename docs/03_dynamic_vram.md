# 동적 분석 — 세이브스테이트 VRAM (RetroArch Beetle Saturn)

날짜 2026-07-11. 입력: 사용자 제공 세이브스테이트 4장(state0=이름입력, state1~3=대사) + 스크린샷.
도구 `tools/parse_state.py`, `scripts/render_vram.py`.

## RZIP 세이브스테이트 포맷 (재도출·확정)

RetroArch Beetle Saturn `.state`:
```
0x00  6B  "#RZIPv"
0x06  1B  버전(01)
0x07  1B  미상(0x23)
0x08  4B  LE block_size (0x20000)
0x0C  8B  LE total_size (0x687480 = 6,845,568B)   ← 옛 Terra 기록의 "BE"는 오류
0x14  ...  청크들 [4B LE clen][zlib] 반복 (첫 청크도 프리픽스 있음 ← 옛 기록 오류)
```
해제 결과 = 6.85MB 새턴 전체 스냅샷. 비압축 `.state`도 자동 처리(parse_maybe_plain).

## 스냅샷 내 메모리 위치 (state0 기준)

| 영역 | 스냅샷 오프셋 | 크기 | 비고 |
|---|---|---|---|
| VDP1 VRAM | 0x7B825 | 0x80000 | Mednafen 변수 `VRAM` (VDP1 섹션) |
| VDP2 VRAM | 0x2FC7FF | 0x80000 | Mednafen 변수 `VRAM` (VDP2 섹션) |
| Work RAM High | 0x57F3D7 (=1ST@0x5833D7 − 0x4000) | 0x100000 | ⚠️ **16비트 바이트스왑 저장** — swap16 복원 필요 |
| CRAM/VDP2 reg | 0x2FC476~ | - | 섹션 태그로 탐색 |

- Mednafen 변수 구조: `[name_len:1B][name][size:4B LE][data]`.
- Work RAM은 swap16 되어 저장됨(1ST.BIN 선두 시그니처가 swap16으로만 매치). VDP2 VRAM은 스왑 여부 미확정(비트맵이 셀단위라 판단 보류).

## ★ 핵심 발견: 대사 텍스트 = 8bpp 셀 비트맵 블릿

- state1 vs state3(다른 대사) VDP2 VRAM diff → **변경이 오직 0x044800–0x048800(≈16KB)에 집중**. 나머지 VRAM 불변.
- 이 영역 바이트값이 단 3종(0x00=배경, 0x07, 0x16=글자색/외곽선) → **타일맵 PND가 아니라 픽셀 데이터**.
- 8x8 셀(8bpp, 64B/셀)로 렌더 시 일본어 마침표 "。"·글자 형태 확인.
- **결론**: 대사 텍스트는 폰트 타일 인덱스 참조가 아니라, **엔진이 글리프 비트맵을 VDP2 VRAM bank A1(0x25E40000대)에 8bpp 셀로 직접 블릿**한다 (Terra의 12×12 블릿 엔진과 동일 계열). 글리프는 프리로드(대사 바뀌어도 글리프 소스 불변).
- ⚠️ saturn.md의 "타일 인덱스 직접 인코딩" 모델은 이 게임엔 **부분적으로만** 적용 — 실제는 블릿 렌더. 인코딩(텍스트바이트→글리프)과 폰트 소스(글리프 테이블)를 별도로 찾아야 함.

## ★ 파일 로더 발견 (1ST.BIN 0x06014600) — 파일→로드주소 매핑

함수 0x06014600이 R8=`load_file(name=R4, dest=R5)`를 반복 호출. 부트/인트로 로드셋:

| 파일 | 로드 주소 | 비고 |
|---|---|---|
| X01.BIN | 0x0603D800 | 스크립트/코드 오버레이 |
| X03.BIN | 0x0602C000 | |
| X06.BIN | 0x06058000 | |
| X02.BIN | 0x06065000 | |
| X04.BIN | 0x060BA000 | |
| X05.BIN | 0x060CC000 | |
| X09.BIN | 0x00200000 | WRAM Low |
| X07.BIN | 0x0609D000 | |
| X2SAMPLE.MES | 0x00218000 | WRAM Low, 인트로 메시지 |
| XINTRNL.CHR | 0x002FE000 | WRAM Low, 내부 스프라이트(폰트 아님) |
| **DEBUG.FNT** | **0x25E40000** | **VDP2 VRAM 텍스트 뱅크에 직접 로드** |

- `load_file` 루틴(R8 주소) 자체가 파일명→ISO 조회→로드. 이후 다른 로더 호출로 씬별 파일이 추가 로드될 것.

## ★ DEBUG.FNT = 8x8 ASCII/기호 폰트 (확정)

8bpp 8x8 셀로 렌더 → `!"#$…0-9…A-Z…a-z…¥` 깨끗한 128글리프 ASCII 폰트. 이름입력 화면의
"英字・記号"·숫자에 쓰이는 소형 폰트. VDP2 VRAM 0x25E40000에 상주.
⚠️ 옛 조사(1bpp 렌더 실패로 "디버그용")는 **오판** — 포맷이 8bpp였음.

## 미해결: 한자 대사 폰트 소스

- 대사 한자는 VRAM에 8bpp로 블릿돼 있으나 **소스(글리프 테이블) 위치 미확정**.
- DEBUG.FNT(8x8 ASCII)·XINTRNL.CHR(5.6KB 스프라이트) 둘 다 아님.
- 가설: (a) 씬과 함께 로드되는 한자 서브셋(state1~3 같은 森 씬이라 글리프 공유), (b) 별도 대형 파일, (c) 블릿이 읽는 WRAM 폰트 테이블.
- **다음 최우선**: state1(대사 씬) Work RAM(High/Low, swap16 복원) 16x16/12x12 1bpp·2bpp 렌더로 한자 글리프 시트 탐색. 또는 텍스트 블릿 루틴(0x25E44800 기록 코드) 정적 추적.

## ★ 텍스트 엔진 골격 규명 (X02.BIN)

de-swap한 WRAM에서 텍스트뱅크(0x25E4xxxx) 참조 코드를 xref로 추적한 결과:

- **X02.BIN = 텍스트 엔진 오버레이** (파일로더가 0x06065000에 로드, 84,472B). 코드임(1bpp 렌더=노이즈).
- **텍스트 합성 버퍼 `0x0607A200`** (0x0E80=3712B, X02 끝 바로 뒤 WRAM) — 글리프가 여기 8bpp로 그려진 뒤
  `copy(dst=0x25E42000 VDP2VRAM, src=0x0607A200, cnt=0x0E80)` (@0x0606FD00, memcpy 0x0600ECD4)로 VRAM 전송.
- **텍스트 상태 구조체** 0x0607A100~0x0607A1E0 (15슬롯 배열: 슬롯당 좌표/색/문자수 등).
- **문자 처리 루틴** 0x060694C8 — 모드(R11 0~12) 점프테이블 디스패치. 슬롯 처리 루프(#0x0F=15).
- **per-char 함수** 0x06065254 (문자폭/측정 추정).
- 배경/이펙트 렌더는 별개 클러스터(0x06048xxx가 0x25E5~E7 VRAM 직접 기록).

## 미해결: 한자 폰트 소스 (다음 세션 핵심)

- DEBUG.FNT(8x8 ASCII)·XINTRNL.CHR(스프라이트)·X02.BIN(코드) 모두 한자 폰트 아님.
- WRAM 밀도스캔은 8bpp 그래픽(포트레이트/배경)을 다 잡아 거짓양성 → 무효.
- **핵심 가설**: 렌더 출력이 8bpp이므로 **한자 폰트 소스도 8bpp일 것** → 1bpp 렌더로는 노이즈로 보였음.
  다음: (a) 합성버퍼 0x0607A200에 픽셀을 쓰는 X02 내 글리프 블릿 루틴을 정적 추적해 폰트 소스 포인터 확보,
  (b) WRAM에서 값이 {0x00 + 소수 팔레트인덱스}로만 채워진 글리프크기 8bpp 영역 탐색, (c) 폰트 압축 가능성.
